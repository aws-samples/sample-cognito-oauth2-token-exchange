🔄 OAuth 2.0 Token Exchange — Global Identity Demo

Country IdP → Token Exchange → Global Identity Token (RFC 8693)

⚙️ Stack Configuration

⚠ Demo only — not a production pattern. This browser demo holds the confidential service client secret client-side and builds the Basic auth header in JavaScript solely to illustrate the exchange request. A confidential client secret must live only in a backend you control — never in browser or mobile code. In production, perform the token exchange from a server-side component and restrict the API's CORS to that origin.
1
Authenticate with Country IdP
User logs in via their local country identity provider
This simulates a user logging into their local country app (e.g. Example Insurance). The user authenticates with the Country IdP and receives an access token — this is the local subject token that will be exchanged for a global identity token.

In production, this would be a browser-based OAuth flow and could include social login (Google, etc.).
↓
2
Exchange for Global Identity Token
RFC 8693 token exchange — country token → global token
The mobile app backend calls the token exchange endpoint with the country token and its own service credentials. Behind the scenes:

1. Lambda Authorizer validates the app's service credentials
2. TokenExchange Lambda verifies the country token cryptographically
3. Cognito custom auth flow issues a global identity token
4. PreTokenGeneration Lambda embeds the local user identity as custom claims

This bypasses Cognito's 5-linked-identity limit — the linking is logical (via claims), not a native federation link.
↓
3
Inspect & Compare Tokens
See the N:1 identity mapping — local user → global identity
The global token carries the user's global identity as the subject, with the country-specific identity preserved in custom claims. Multiple country identities (Germany, Swiss, Direct) can all map to the same global identity.

Notice how the broad aws.cognito.signin.user.admin scope has been replaced with specific global scopes — enforcing least privilege.
↓
4
Verification Extensibility
Non-standard IdPs and custom token formats
Not all country IdPs produce standard JWTs. The VerifyAuthChallenge Lambda is the extensibility point — you have full control over how the incoming token is verified.
Option A: Verification API
// Country exposes /verify
const resp = await fetch(
  COUNTRY_VERIFY_URL,
  { headers: { token } }
);
answerCorrect = resp.ok;
Option B: Shared Key
// Verify with HMAC/RSA key
const key = await getKey();
const decoded = jwt.verify(
  token, key
);
answerCorrect = !!decoded;
Option C: Custom Format
// Not even a JWT
const parsed =
  parseCustomToken(token);
answerCorrect =
  isValid(parsed);
The output is always a standard Cognito JWT from the Global Identity Pool — regardless of what went in.
